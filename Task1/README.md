# Задание 1. Исследование моделей и инфраструктуры

## Постановка задачи

Заказчик - руководство QuantumForge Software (продуктовая компания, Хельсинки/Таллин), задача поставлена в рамках инициативы по сокращению времени поиска информации в корпоративной базе знаний. Получатели результата - разработчики, саппорт, менеджеры/аналитики и новые сотрудники, которые будут пользоваться RAG-ботом.

Ключевые ограничения кейса, которые влияют на выбор стека:

- часть базы знаний - это внутренние архитектурные решения, API-документация и данные консалтинговых проектов клиентов (ABB, Wärtsilä, энергокомпании). Такие материалы могут подпадать под NDA и требования SOC 2, поэтому отправка их в облачный API третьей стороны - риск.
- компания уже полностью в AWS (EKS + RDS), есть Kubernetes-инфраструктура и команда DevOps, то есть локальный хостинг моделей и векторной БД технически реализуем без больших дополнительных затрат на платформу.
- объём базы знаний уже сейчас большой (~18 000 MD/MDX, ~3 000 страниц Confluence, ~250 PDF) и растёт на ~400 страниц в месяц - значит, важна не только разовая стоимость индексации, но и стоимость постоянного пере-индексирования.
- готовится SOC 2 yearly review - любое решение, которое передаёт конфиденциальные данные внешнему провайдеру, увеличивает объём работы GRC-команды по аудиту.

Эти ограничения задают вектор: там, где данные чувствительные, предпочтительнее локальные модели, а облачные API оставить для менее чувствительных задач или как опцию с фильтрацией контента.

## 1. Сравнение LLM-моделей

### Локальные модели (Hugging Face, например Llama 3, Mistral, Qwen)

- **Качество ответов**: у топовых открытых моделей (Llama 3 70B, Mixtral 8x22B, Qwen2.5 72B) качество на уровне GPT-3.5/GPT-4o-mini для задач вопрос-ответ по документам, но заметно уступает GPT-4o/YandexGPT Pro на сложных рассуждениях и работе с редкими форматами (таблицы, код на Go/Python вперемешку). Для RAG, где модель в основном пересказывает найденный контекст, разрыв в качестве меньше, чем в задачах "чистого знания".
- **Скорость работы**: зависит от железа. На GPU (A100/H100) генерация быстрая (десятки токенов/сек), на CPU - неприемлемо медленная для интерактивного бота. Требует отдельного inference-сервера (vLLM, TGI) для приемлемой скорости под нагрузкой нескольких пользователей одновременно.
- **Стоимость владения**: нет платы за токен, но нужен GPU-инстанс (аренда или собственный), который работает постоянно или почти постоянно - это фиксированные расходы независимо от фактической нагрузки. При низкой и неравномерной нагрузке (внутренний корпоративный бот) может быть дороже, чем pay-per-use API.
- **Удобство и простота развёртывания**: сложнее - нужно поднять inference-сервер, настроить квантование, следить за версиями моделей, обновлять веса. Требует DevOps/MLOps-компетенций, которые у команды есть (EKS, Helm), но это дополнительная нагрузка на инфраструктурную команду.

### Облачные модели (OpenAI GPT-4o/4o-mini, YandexGPT)

- **Качество ответов**: стабильно высокое, особенно у GPT-4o на сложных запросах и мультиязычных документах (важно, так как компания финско-эстонская, документация может быть на нескольких языках). YandexGPT слабее на английской технической документации, но приемлем для русскоязычных материалов и дешевле для российских клиентов.
- **Скорость работы**: как правило, выше и стабильнее локальных решений на CPU, сравнима с локальными на GPU, плюс не нужно самим управлять масштабированием под пиковую нагрузку.
- **Стоимость владения и использования**: нет капитальных затрат на GPU, оплата по токенам. При умеренной нагрузке (внутренний бот, не миллионы запросов) это обычно дешевле, чем держать выделенный GPU-инстанс 24/7. При росте нагрузки стоимость растёт линейно и может превысить локальное решение.
- **Удобство и простота развёртывания**: минимальное - вызов HTTP API, нет забот с весами моделей и GPU. Быстрее всего для MVP.

### Вывод по LLM

Основной риск - конфиденциальные данные консалтингового направления и материалы, подпадающие под SOC 2. Рекомендация: гибридная схема. Для документов с грифом "confidential"/клиентских данных - локальная модель (Llama 3 / Qwen2.5 через vLLM на своём GPU-инстансе в VPC). Для общей внутренней документации (архитектура, onboarding, регламенты без клиентских данных) - облачный API (GPT-4o-mini как баланс цена/качество), так как это ускоряет MVP и снижает нагрузку на DevOps.

## 2. Сравнение моделей эмбеддингов

### Локальные (Sentence-Transformers, например multilingual-e5-large, bge-m3)

- **Скорость создания индекса**: при наличии GPU - высокая (тысячи документов в минуту), на CPU заметно медленнее, но для батчевой ночной переиндексации (прирост ~400 страниц/месяц) это не критично даже на CPU.
- **Качество поиска**: современные открытые модели (bge-m3, e5-large-v2) по бенчмаркам (MTEB) сопоставимы или превосходят OpenAI text-embedding-3-large на многих доменах, особенно с дообучением/fine-tuning на своих данных. Модели типа bge-m3 и e5 хорошо поддерживают мультиязычность (важно для EN/RU/FI-документов компании).
- **Стоимость владения**: разовая инференс-нагрузка на GPU/CPU, нет платы за токен. При объёме ~18 000+ файлов и регулярной переиндексации это существенно дешевле в долгосрочной перспективе.

### Облачные (OpenAI text-embedding-3-small/large)

- **Скорость создания индекса**: высокая и стабильная, не зависит от своего железа, но упирается в rate limits API при массовой индексации (десятки тысяч документов).
- **Качество поиска**: text-embedding-3-large - один из сильнейших вариантов "из коробки" без дополнительной настройки, хорошо работает без fine-tuning.
- **Стоимость владения и использования**: оплата по токенам за каждую индексацию/переиндексацию. При объёме базы в 20+ тысяч документов и ежемесячном приросте это регулярные расходы, растущие пропорционально объёму базы, плюс отправка всего контента (включая потенциально конфиденциального) во внешний сервис.

### Вывод по эмбеддингам

Для эмбеддингов конфиденциальность критичнее, чем для генерации ответа: эмбеддинги индексируют весь корпус целиком, включая закрытые документы. Рекомендация - локальная модель эмбеддингов (bge-m3 или multilingual-e5-large) для всего корпуса без исключений. Это также снимает вопрос rate limits при первоначальной индексации ~21 000 документов и делает стоимость предсказуемой независимо от роста базы.

## 3. Сравнение векторных баз: ChromaDB vs FAISS

### FAISS

- **Скорость поиска и индексации**: очень высокая, особенно с индексами типа HNSW/IVF, оптимизирован Meta для больших объёмов векторов, хорошо работает на GPU.
- **Сложность внедрения и поддержки**: это библиотека, а не сервис - нет встроенного хранения метаданных, персистентности "из коробки", REST API, авторизации и поддержки конкурентного доступа/обновлений на лету. Всё это (сохранение индекса на диск, версионирование, метаданные, фильтрация по атрибутам) нужно реализовывать самостоятельно поверх LangChain.
- **Удобство в работе**: хорошо для одноразовых/batch-сценариев и прототипов, менее удобен как долгоживущий сервис с частыми обновлениями (например, когда документ поменялся в Confluence и нужно обновить только его вектора).
- **Стоимость владения**: минимальна на старте (просто библиотека в процессе бота), но при росте требований (multi-tenant, real-time апдейты, метаданные для фильтрации по пространству Confluence/языку/актуальности) стоимость доработки растёт.

### ChromaDB

- **Скорость поиска и индексации**: на средних объёмах (сотни тысяч - единицы миллионов векторов) сопоставима с FAISS, при очень больших объёмах и высоконагруженном поиске FAISS обычно быстрее за счёт более зрелых ANN-индексов.
- **Сложность внедрения и поддержки**: работает как отдельный сервис (клиент-сервер) или embedded-режим, из коробки даёт персистентность, хранение метаданных, фильтрацию по метаданным (например, "только страницы из пространства DEV, обновлённые за последние 3 месяца"), можно развернуть в Kubernetes как отдельный под с volume - что органично ложится на существующий EKS-стек компании.
- **Удобство в работе**: выше за счёт API уровня "документ + метаданные + upsert/delete", что удобно для инкрементальных обновлений базы знаний (задание 6 про ежедневное обновление) - не нужно пересобирать индекс целиком.
- **Стоимость владения**: выше на старте (нужен отдельный под/сервис, диск под персистентность), но ниже в поддержке при частых инкрементальных обновлениях, так как не требует ручной реализации персистентности и upsert-логики.

### Вывод по векторной БД

Так как база знаний QuantumForge растёт непрерывно (~400 страниц/месяц) и требует ежедневного автообновления (задание 6) с удалением устаревших и добавлением новых документов, важнее удобная инкрементальная работа с метаданными, чем чистая скорость поиска на пределе миллиардов векторов. **Рекомендуется ChromaDB** как основная векторная БД для продакшн-варианта: встроенная персистентность, метаданные и upsert/delete делают её удобнее для растущей и часто обновляемой базы, и она разворачивается как обычный сервис в существующем EKS-кластере. FAISS стоит оставить как вариант для локальных экспериментов/прототипирования на этапе разработки (задания 2-4 этого спринта), где не нужна персистентность и инкрементальные обновления.

## 4. Рекомендуемая конфигурация сервера

Исходя из выбора "локальные эмбеддинги + локальная LLM для конфиденциальных данных + ChromaDB", минимальная конфигурация для продакшн-инстанса RAG-бота:

- **CPU**: 8-16 vCPU - для ChromaDB, обработки запросов, оркестрации LangChain, а также инференса эмбеддингов на CPU в непиковые часы (переиндексация ночью).
- **RAM**: 32-64 ГБ - индекс эмбеддингов на ~20 000+ документов (с учётом чанкования - несколько сотен тысяч векторов), кэш ChromaDB и буферы для конкурентных запросов.
- **GPU**: 1x GPU уровня NVIDIA A10G/L4 (24 ГБ VRAM) - достаточно для инференса квантованной 7B-13B локальной LLM (например, Qwen2.5-14B-Instruct в 4-бит) и локальной модели эмбеддингов (bge-m3) с приемлемой задержкой. Для более крупных моделей (70B) потребуется A100 (40-80 ГБ VRAM) или несколько GPU, но для внутреннего корпоративного бота с умеренной нагрузкой 7B-14B модели достаточно.
- **Диск**: SSD от 200 ГБ - хранение персистентных данных ChromaDB, весов моделей (десятки ГБ на модель) и логов.
- **Сеть**: размещение в приватном VPC-сегменте существующей AWS-инфраструктуры (EKS), без публичного доступа к inference-эндпоинтам, доступ только через внутренний API Gateway/бот.

## Итоговые рекомендации: варианты конфигурации

### Вариант A. Полностью облачный (OpenAI + FAISS)

LLM - GPT-4o-mini, эмбеддинги - text-embedding-3-small, векторная БД - FAISS (embedded, без отдельного сервиса).

- Плюсы: самый быстрый старт, минимум DevOps-работы, высокое качество ответов из коробки.
- Минусы: весь корпус документов (включая конфиденциальные материалы консалтинга) уходит во внешний API - конфликт с требованиями SOC 2 и NDA клиентов; растущая стоимость по мере роста базы и нагрузки; FAISS неудобен для ежедневных инкрементальных обновлений.
- Для кого подходит: быстрый пилот/PoC на нечувствительных данных (например, только onboarding-документация).

### Вариант B. Полностью локальный (Hugging Face + ChromaDB)

LLM - Qwen2.5-14B-Instruct через vLLM, эмбеддинги - bge-m3, векторная БД - ChromaDB на EKS.

- Плюсы: полный контроль над данными, ничего не покидает периметр компании, предсказуемая стоимость (в основном инфраструктурная, не растёт с числом запросов), упрощает прохождение SOC 2 review.
- Минусы: выше стартовые затраты на GPU-инстанс и настройку inference-сервера, требует MLOps-компетенций для обновления моделей и мониторинга качества, чуть ниже итоговое качество ответов на сложных мультиязычных запросах по сравнению с GPT-4o.
- Для кого подходит: продакшн-сценарий для всей базы знаний компании, где есть конфиденциальные и клиентские данные.

### Вариант C. Гибридный (рекомендуемый)

Эмбеддинги - локальные (bge-m3) для всего корпуса. Векторная БД - ChromaDB. LLM - маршрутизация: локальная модель (Qwen2.5-14B) для запросов, затрагивающих закрытые пространства Confluence/консалтинговые проекты, и облачная (GPT-4o-mini) для запросов по открытой внутренней документации (архитектура, onboarding, регламенты без клиентских данных).

- Плюсы: закрывает риск утечки конфиденциальных данных именно там, где он есть (эмбеддинги индексируют всё, поэтому они всегда локальные), даёт лучшее качество ответов на "безопасных" данных через облачный API, гибко балансирует стоимость - GPU нагружен только частью трафика.
- Минусы: сложнее в реализации, чем моно-вариант (нужна логика маршрутизации по источнику документа/пространству), два пути тестирования и мониторинга качества вместо одного.
- Для кого подходит: кейс QuantumForge - смешанный характер данных (открытая внутренняя документация + конфиденциальные консалтинговые материалы), требования SOC 2, растущая база с частыми обновлениями.

### Вариант D. Полностью локальный на CPU (бюджетный)

LLM - Mistral-7B-Instruct в 4-бит квантовании на CPU, эмбеддинги - all-MiniLM-L6-v2 (лёгкая модель) на CPU, векторная БД - ChromaDB.

- Плюсы: минимальные затраты на инфраструктуру (нет GPU), подходит для очень ограниченного бюджета или пилота на небольшом поднаборе документации.
- Минусы: неприемлемая скорость ответа для интерактивного использования при сколько-нибудь заметной нагрузке (десятки секунд на ответ), заметно более низкое качество эмбеддингов и генерации на большом мультиязычном корпусе.
- Для кого подходит: только как временное решение для локальной разработки и тестов (задания 2-5 текущего спринта), не для продакшна.

### Выбор

Для продакшн-решения QuantumForge Software рекомендуется **вариант C (гибридный)**: локальные эмбеддинги и ChromaDB закрывают требование конфиденциальности и удобство инкрементальных обновлений растущей базы знаний, а маршрутизация LLM-запросов между локальной и облачной моделью даёт баланс между качеством ответов и защитой чувствительных данных без избыточных затрат на GPU для всего трафика. Для выполнения текущего спринта (прототип бота) в заданиях 2-5 используется более простая связка - локальные эмбеддинги + FAISS как embedded-хранилище для быстрой итерации, с переходом на ChromaDB на этапе продакшн-развёртывания (задание 6, автообновление).
